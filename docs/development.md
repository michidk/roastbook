# Development and testing

## Prerequisites

- Bun 1.4.4
- PostgreSQL for development and database integration tests
- Docker for the complete stack or S3 integration tests

```bash
bun install --frozen-lockfile
cp .env.example .env   # point DATABASE_URL at a development database
bun run dev            # http://localhost:3000
```

The development server has no Hodor in front of it but uses the same request
authentication and RLS boundary as production. Set `AUTH_ENABLED=true` and
configure email delivery (a local SMTP capture service works) to exercise
built-in accounts. Run `bun run worker` separately to process exports and
account deletion.

The server applies pending committed migrations before accepting requests and
again when Vite restarts. Migrations generated while Vite runs are applied and
trigger a full reload. A failure at startup stops the server; a failure seen by
the watcher is logged.

## AI adapter dependency patch

Bun applies the committed `@tanstack/openai-base@1.0.0` patch during installation.
It preserves token usage on Responses `response.failed` and
`response.incomplete` events; the shared request runner records that usage
when handling the SDK's terminal error event. Both Docker stages copy the
patch before installing dependencies. When upgrading the adapter, run
`src/lib/server/ai-request.server.test.ts` and remove the patch once upstream
preserves usage on both events.

## Component stories

```bash
bun run storybook        # http://localhost:6006
bun run build:storybook  # static site in storybook-static/
```

Storybook needs no database, storage or API credentials. Its toolbars switch
theme and the 375px, 768px and 1280px viewports; Controls edit props and Actions
record callbacks. Stories with a `play` function run interaction assertions.
Build Storybook when changing its configuration or stories.

Stories live beside components as `*.stories.tsx`; configuration is in
`.storybook/`. The preview provides the real stylesheet, tooltip provider,
toasts and an in-memory router with fictional settings (override with
`parameters.appSettings`). Links use memory history. Stories cover reusable
presentation components; service-connected containers (saving forms, image
persistence, AI, entity search, live maps, settings, sync) remain integration
coverage. The picture uploader previews local files and rejects URL imports.
Keep page-height and map-positioning adjustments inside story wrappers.

## Database workflow

`bun run db:migrate` applies the migrations in `drizzle/`. The development
server, Docker Compose, CI and the Helm migration job all use it.

For a schema change:

1. Update `src/db/schema.ts`.
2. Run `bun run db:generate` and review the SQL and `drizzle/meta` changes.
3. Run `bun run db:migrate` against a disposable database.
4. Run the database integration tests.
5. Commit the migration and its metadata together.

| `bun run` script | Purpose |
| --- | --- |
| `db:push` | Push the schema without a migration (throwaway databases) |
| `db:migrate:cli` | Raw Drizzle Kit `migrate` |
| `db:studio` | Drizzle Studio |
| `db:seed` | Load the demo's records and images into an empty database |

Run `bun run generate-routes` after route-file changes; never edit
`src/routeTree.gen.ts`.

## API response schemas

Run `bun run generate:api-responses` after changing an integration handler's
return type or adding an operation. Commit
`src/lib/server/integrations/response-schemas.gen.json` with the code change;
do not edit it by hand. The generator reads the operation catalog's inferred
return types, maps dates to ISO strings and void results to null, and supplies
the success schemas in `/api/v1/openapi.json`. `bun run check` rejects stale
response schemas.

## Journal functions

Journal reads and writes are SQL functions in `src/journal/`; see
[Journal architecture](client-data.md). `bun run check:boundaries` enforces that
journal code uses only `src/journal/platform/*`. New journal tables need owner
revision triggers, generated by
`bun scripts/generate-journal-sync-triggers.ts`. The browser applies the same
committed migrations, so never edit a released migration.

## Tests and quality checks

```bash
bun run check               # Biome, import boundaries, markdownlint
bun run typecheck
bun run test                # unit tests and browser-runtime tests
bun run lint:deadcode
bun run build
bun run check:client-assets
bun run check:pwa
```

`bun run verify` runs this sequence in order.

- `test` lets environment-dependent integration suites skip and includes
  `test:browser-runtime`, which runs `*.browser.test.ts` journal functions on
  in-process PGlite. `test:unit` excludes integration suites;
  `test:coverage` reports coverage without a threshold.
- `check:client-assets` enforces JavaScript and MapLibre chunk budgets and
  rejects server-only SDK code in browser assets. Pass another build's public
  directory to check it, e.g. `dist/client`.
- `check:pwa` validates the manifest, icons, offline page and built service
  worker.

`bun run test:integration` is strict and needs isolated services:

- `TEST_DATABASE_URL`
- `TEST_S3_ENDPOINT`
- `TEST_S3_ACCESS_KEY_ID`
- `TEST_S3_SECRET_ACCESS_KEY`
- `TEST_S3_BUCKET`

It runs each suite in its own process and fixes image limits (three pictures
per item, 1 MiB per journal). The authentication contract in
`scripts/auth-contract.ts` runs there without sending external email.

CI provisions PostgreSQL and MinIO, runs all tests, checks the database schema
against its migration snapshots, builds the demo with the same asset checks,
and runs actionlint. Workflows with `@orcastrate`
frontmatter are rendered from
[`michidk/workflows`](https://github.com/michidk/workflows); change the template
too, or the next sync reverts the edit.

Run the standard and demo builds one at a time in a checkout; they share Nitro
build state.

## Progressive web app

The service worker is registered only in production builds. To test it:

```bash
bun run build
bun run start
```

Use HTTPS or `http://localhost`. In the browser's Application panel, check the
manifest and service worker, then go offline and reload. Unregister the worker
there before returning to `bun run dev` on the same origin. Offline behavior is
described in [Offline journaling](offline.md); `scripts/service-worker.test.ts`
covers the worker's runtime behavior.

The demo (`bun run dev:demo`, `bun run build:demo`) has no install manifest or
server sync; see [Browser-local demo](demo-mode.md).

## Browser QA

Check changed routes at 375px, 768px and 1280px, including keyboard access,
loading, empty and error states, console errors and failed requests. Keep
temporary screenshots and recordings in `.artifacts/qa/` (ignored); do not add
browser automation dependencies or generated tests.

## Maintenance scripts

| `bun run` script | Purpose |
| --- | --- |
| `storage:backfill-thumbnails` | Add missing thumbnails under `STORAGE_PATH` |
| `storage:orphans` | Report stored media without a database record |
| `db:duplicate-roasters` | Report roasters with colliding names |

`bun run db:duplicate-roasters --merge` moves beans to the roaster with the most
beans (then the oldest) and deletes the duplicates.
